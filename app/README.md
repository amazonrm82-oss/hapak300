# כשירות חפ״ק מח״ט 300 — המערכת האמיתית

מימוש ייצור של האב-טיפוס שנבנה ב-Claude Design (`../project/`), לפי המפרט ב-`../project/design_handoff_hapak300/`.

**Next.js 14 (App Router) + TypeScript + Supabase** — נתונים משותפים לכל המשתמשים, הרשאות שנאכפות בבסיס הנתונים, התראות אמיתיות, ואפליקציה להתקנה בטלפון (PWA).

> האב-טיפוס בתיקיית `project/` נשאר כמו שהוא ואינו חלק מהמערכת הזו — הוא המקור לעיצוב ולכללים, לא קוד שרץ.

---

## 1. איך זה בנוי לפריסה

אין שלב build מקומי ואין CLI. הקוד יושב ב-GitHub, **Vercel** מושך ובונה אותו,
ו-**Supabase** מקבל את הסכמה בהדבקה אחת בדפדפן. כל לוגיקת השרת — הכניסה
והתזכורות — היא Route Handlers של Next.js, ולא Supabase Edge Functions, כדי
שההקמה לא תדרוש להתקין דבר על מחשב היעד.

| מה | איפה רץ |
|---|---|
| מסכים | Next.js (Vercel) |
| כניסה: `POST /api/auth/login`, `/api/auth/set-pin` | Node runtime, service-role key |
| תזכורות: `POST /api/cron` | Node runtime, מוגן ב-`CRON_SECRET` |
| מזג אוויר: `GET /api/weather` | Node runtime |
| נתונים, הרשאות, Realtime, Storage | Supabase |
| תזמון | `pg_cron` + `pg_net` בתוך Supabase, קורא ל-`/api/cron` |

> **המדריך המלא להקמה, צעד אחר צעד ובלי ידע קודם, נמצא ב-[`מדריך-התקנה.md`](./%D7%9E%D7%93%D7%A8%D7%99%D7%9A-%D7%94%D7%AA%D7%A7%D7%A0%D7%94.md).**
> הסעיפים כאן הם התקציר למפתחים.

## 2. הקמה מהירה

1. **Supabase → New project.** מ-Project Settings → API קח `Project URL`, `anon public`, `service_role`.
   > ה-`Project URL` הוא הבסיס בלבד — `https://xxxx.supabase.co`, **בלי** `/rest/v1/`.
2. **SQL Editor → New query** → הדבק את כל `supabase/setup.sql` → **Run**.
   קובץ אחד שמכיל את כל המיגרציות והנתונים ההתחלתיים, ורץ כטרנזקציה אחת.
3. **Database → Extensions** → הפעל `pg_cron` ו-`pg_net`.
   > בסיס נתונים שכבר הוקם לפני עדכון מסוים לא מקבל אותו מ-`setup.sql` (הוא
   > נכשל על טבלאות קיימות). לעדכון בסיס קיים — ראה ״עדכון בסיס נתונים קיים״
   > מיד למטה.
4. **Vercel → Import** את הריפו, **Root Directory = `app`**, והוסף את משתני הסביבה מסעיף 3.
   > **Settings → Deployment Protection → Vercel Authentication = Disabled.**
   > כשההגנה דלוקה, Vercel מציג מסך התחברות **משלו** לפני האתר — ולוחם בלי
   > חשבון Vercel פשוט לא נכנס. מי שנכנס לאפליקציה אמור לראות את מסך המספר
   > האישי והקוד, ותו לא. השמירה על הנתונים היא ה-RLS והקוד, לא שער של Vercel.
5. אחרי הפרסום — הרץ ב-SQL Editor את פקודת ה-`cron.schedule` מסעיף 5 כאן,
   עם כתובת האתר וה-`CRON_SECRET` שלך.

### עדכון בסיס נתונים קיים

**אין צורך לדעת מה כבר הורץ.** שתי הדבקות, בסדר הזה, ב-SQL Editor:

1. `supabase/update-1.sql` → Run
2. `supabase/update-2.sql` → Run
3. `supabase/verify.sql` → Run — טבלה של ✅ מול כל יכולת. שורה עם ❌ אומרת
   שהדבקה נעצרה באמצע; הרץ אותה שוב.

שני קבצים ולא אחד בגלל מגבלת Postgres: ערך חדש ברשימת הצוותים חייב להישמר
לפני שאפשר להשתמש בו, והעורך של Supabase מריץ הדבקה אחת כטרנזקציה אחת.

מה שכאן בטוח להריץ שוב ושוב: מה שקיים נשאר, מה שחסר נוסף, ושום לוחם, אימון
או סימון נוכחות לא נמחק. זה נבדק על בסיס ישן, על בסיס מעודכן ועל שלוש הרצות
רצופות — ובכל המקרים התוצאה זהה בדיוק לסכימה של התקנה נקייה מ-`setup.sql`.

הקבצים נבנים מקובצי ה-`patch-NN-*.sql` על ידי `node supabase/build-update.mjs`;
אחרי הוספת patch חדש יש להריץ אותו, אחרת הקבצים יישארו מאחור.

## 3. משתני סביבה

ב-Vercel: **Settings → Environment Variables**. מקומית: `cp .env.local.example .env.local`.

| משתנה | סוד? | מה זה |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | לא | כתובת הפרויקט |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | לא | מפתח הדפדפן |
| `SUPABASE_SERVICE_ROLE_KEY` | **כן** | קורא `pin_hash` ומנפיק סשנים |
| `PIN_PEPPER` | **כן** | מגן על קודי הכניסה. ⚠️ אין לשנות אחרי שנבחרו קודים |
| `AUTH_DERIVE_SECRET` | **כן** | ממנו נגזרת סיסמת ה-Auth |
| `CRON_SECRET` | **כן** | מוכיח שהקורא ל-`/api/cron` הוא המתזמן |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | לא | רשות — פוש |
| `VAPID_PRIVATE_KEY` | **כן** | רשות — פוש |

לסודות אין קידומת `NEXT_PUBLIC_`, ולכן Next.js לא אורז אותם לצד הלקוח.

## 5. התזכורות

`/api/cron` מבצע פעם בכל הרצה:

- תזכורת ערב לפני, בשעה שנקבעה בהגדרות (18:00)
- תזכורת שעתיים לפני היציאה
- "ממתין לסיכום" יום אחרי אימון שעבר
- הזמנה ללא מענה מעל 48 שעות
- הסמכה שפוקעת בתוך 30 יום

כל אירוע נשלח **פעם אחת** — המפתח הראשי של `reminders_sent` הוא מה שמבטיח זאת.
באותו מעבר נשלח גם Web Push לכל התראה שטרם נשלחה, לפי העדפות ההתראות של כל אדם.

### הפעלת התזמון

הפקודה הזו אינה חלק מ-`setup.sql` בכוונה — ביטוי ה-cron שבתוכה מכיל רצף תווים
שסוגר הערת SQL, ודי בכך כדי להפיל קובץ שלם. מריצים אותה פעם אחת ב-SQL Editor
אחרי שהאתר פורסם, עם `<SITE>` = כתובת האתר ו-`<CRON_SECRET>` = אותה מחרוזת
שהוגדרה ב-Vercel:

```sql
select cron.schedule(
  'hapak-automations',
  '*/10 * * * *',
  $$
  select net.http_post(
    url     := '<SITE>/api/cron',
    headers := jsonb_build_object(
                 'Content-Type', 'application/json',
                 'Authorization', 'Bearer <CRON_SECRET>'),
    body    := '{}'::jsonb
  );
  $$
);
```

בדיקה: `select jobname, schedule, active from cron.job;`
עצירה: `select cron.unschedule('hapak-automations');`

### פוש

`npx web-push generate-vapid-keys` → ה-public ל-`NEXT_PUBLIC_VAPID_PUBLIC_KEY`,
ה-private ל-`VAPID_PRIVATE_KEY`. בלעדיהם ההתראות בתוך האפליקציה עובדות כרגיל,
והמסך `/install` אומר במפורש שהפוש עוד לא הופעל בשרת.

הלוחם מפעיל פוש במכשירו מ-**התקנה בטלפון והתראות** (`/install`) או מהפרופיל.
`POST /api/push/test` שולח התראת בדיקה למכשירים של הקורא בלבד — הזיהוי לפי
ה-access token שלו.

## 5א. הצוותים

**צוות א׳** ו**צוות ב׳** מתאמנים בסבב מדורג, ויש גם אימונים משותפים.

**סדיר** הוא צוות שלישי שאינו מתאמן לבד: הוא מצטרף לכל אימון של א׳ או של ב׳.
המשמעות בפועל — לוחמי סדיר מקבלים זימון לכל אימון, מסמנים נוכחות, נכנסים
לצ׳אט, ונספרים במזון, במקומות ברכב ובתחמושת. לכן `team_id` של אימון נשאר
`a`/`b`/`joint` בלבד: אין ״אימון של סדיר״.

זה נשען על `teams.attends_all`, כך שאפשר להוסיף בעתיד עוד צוות שמתנהג כך בלי
לגעת בקוד — רק דגל בשורה בטבלה.

## 5ב. מקצים וציונים

לכל אימון יש לשונית **מקצים** — התחנות שהאימון בנוי מהן: ירי בעמידה, ירי
בתנועה, החלפת מחסנית. לכל מקצה שם, תיאור מה היה בו, וסוג מדידה:

| סוג | איך נמדד |
|---|---|
| ירי | כמה כדורים וכמה פגיעות → הציון מחושב לבד (0–100) |
| ציון ידני | המדריך נותן 0–100 |
| עבר / לא עבר | נשמר כ-100 או 0 |

**הציון של הלוחם באימון** הוא ממוצע משוקלל של המקצים שהוא השתתף בהם — מקצה
שלא השתתף בו אינו נספר לו כאפס, כי ״לא ירה״ ו״לא פגע״ אינם אותו דבר.
**ציון האימון** הוא ממוצע הלוחמים שנמדדו.

מעל הציון המדוד יש את **ציון המפקד**: 1–10 לכל לוחם (נשמר בנוכחות של אותו
אימון) ו-0–100 לאימון כולו, עם נימוק. השניים מוצגים זה לצד זה ולא ממוזגים —
מספר שהמטווח הפיק ומספר שמפקד שקל אינם אותו סוג טענה.

הציון מחושב בטריגר בבסיס הנתונים ולא בדפדפן, כדי ששני מסכים לא יוכלו לחלוק על
מה ש-12 מתוך 20 שווה. יש גם **הדפסת תוצאות** לכל אימון.

## 6. הפעלה ביחידה — סדר הפעולות

1. **כניסה ראשונה** במספר האישי שלך, בחירת קוד.
2. **צוותים** → הוספה מהירה: שם, דרגה, תפקיד, מספר אישי, טלפון, צוות. אף אחד לא יכול להיכנס עד שהוא נמצא ברשימה הזו.
3. בטופס המלא (**עריכה**) של כל לוחם: הרשאות (מפקד צוות / מדריך / מפקד חפ״ק / מנהל), הסמכות הדרכה לפי נושא, והסמכות אישיות עם תאריך תפוגה. מינוי **מנהל מערכת** זמין למנהל מערכת בלבד.
4. **מנה מפקד צוות** לכל צוות — הוא זה שמאשר נוכחות סופית.
5. **לוגיסטיקה → צי הרכבים**: רשום פעם אחת את רכבי היחידה עם הצ׳ שלהם. מכאן והלאה בוחרים אותם מרשימה בכל אימון.
6. **ניהול → יצירת סבב אוטומטי**: תאריך התחלה, יום בשבוע, שעות, מספר שבועות סבב ומשותפים, ובחירת הנושאים. המערכת בונה את כל התקופה — ואפשר לערוך כל שורה בטבלה.
7. כל לוחם נכנס במספר האישי שלו, בוחר קוד, ומתחיל לסמן נוכחות — ומ-**התקנה בטלפון והתראות** מתקין את האפליקציה ומפעיל פוש.

**`src/lib/core/` הוא הלב.** כל הכללים — הרשאות, סטטיסטיקות נוכחות, התרעות למפקד, הצעת מחליף, חישוב כשירות, יצירת סבב, ייצוא — תורגמו אחד-לאחד מ-`hapak-core.js` של האב-טיפוס. שינוי כלל עסקי מתחיל שם.

### הכללים העסקיים, בקצרה
- **נוכחות** — מגיע / מאחר / לא מגיע / חולה-גימלים / מילואים אחר / סיבה חופשית. סיבה **חובה** כשלא ״מגיע״ או ״מאחר״. פתוח עד תחילת האימון. מי שלא הגיב נרשם ״לא מגיע״ באישור הסופי. ״מאחר״ נספר כמגיע.
- **אישור בשתי רמות** — מפקד האימון מסכם ← מפקד הצוות מאשר. באימון משותף מפקד האימון מאשר הכול. מפקד יכול לפתוח מחדש.
- **מחליף אוטומטי** — מוסמך לנושא +4, זמין באותו יום +2, העביר את הנושא בעבר +2, מהצוות השני +1, ‎−0.3 לכל אימון שכבר העביר בתקופה.
- **המפקדה** — תקן, לא מקום לחנות בו אנשים: מח״ט, סמח״ט וקצין אג״ם, אחד מכל אחד, מוזנים ביד על ידי מנהל המערכת או מפקד החפ״ק בלבד. מי שיושב שם אינו שייך לצוות, ולכן מצרף את עצמו לכל אימון שהוא מחליט להגיע אליו. הרשימה היא `STAFF_ROLES` ב-`src/lib/core/constants.ts`, ולה אינדקס ייחודי חלקי לכל תפקיד בבסיס הנתונים.
- **כשירות 1–10** — דירוג מפקד 25% · נוכחות מאושרת 25% · ציון באימונים 25% · ציון המפקד לאימון 25%. רכיב שאין עליו נתונים עדיין (לפני שהסתיים אימון) יורד והשאר מתנרמלים, כדי שצוות חדש לא ייקרא 2.5 רק משום שטרם נמדד. נראית למפקדים בלבד.
- **סיכום** — רשות; ננעל 7 ימים אחרי האימון (מנהל ומפקד חפ״ק פטורים).
- **תחמושת** — כדורים ללוחם × מספר לוחמים, או סה״כ ישיר; ״נוצל בפועל״ מוזן על ידי מפקד האימון; חתימת מפקד אימון על ההקצאה.

## 8. אבטחה

- **כניסה**: מספר אישי (7 ספרות) + קוד (4 ספרות) שהלוחם בוחר בכניסה הראשונה. הקוד נדרש **בכל כניסה** — הסשן נשמר ב-`sessionStorage` ונעלם עם סגירת הלשונית.
- **הקוד** נשמר כ-PBKDF2-SHA256 (210,000 סבבים) עם מלח אישי ו-pepper שנמצא רק בסביבת הפונקציות. אחרי 5 ניסיונות כושלים החשבון ננעל ל-15 דקות.
- **הסיסמה של Supabase Auth אינה הקוד** — היא נגזרת בשרת ממזהה הלוחם, כך שהקוד לא עוזב את פונקציות הכניסה.
- **הרשאות נאכפות ב-RLS**, לא רק בממשק: כל טבלה מוגנת לפי מטריצת ההרשאות. לוחם רגיל לא יכול לקרוא מספרים אישיים של אחרים גם דרך קריאה ישירה ל-API (`people_view` מסתירה אותם), לא יכול לאשר נוכחות של עצמו, ולא יכול לסמן נוכחות אחרי שהאימון התחיל — טריגרים בבסיס הנתונים חוסמים את זה.
- **סדר דרגות ההרשאה** — מנהל מערכת נמצא מעל מפקד החפ״ק. שניהם מנהלים את היחידה, אבל רק מנהל מערכת יכול לערוך מנהל מערכת, למנות אחד, להסיר אחד או לאפס לו את הקוד. נאכף בטריגר `guard_admin_rank`, לא רק בכפתורים.
- **איפוס קוד** — מנהל מערכת או מפקד חפ״ק בלבד, מטופס הלוחם (ולא על מנהל מערכת).
- **מנהל אחרון** — לא ניתן להסיר את הרשאת הניהול האחרונה במערכת.
- **כתיבת התראה** שמורה למנהל, למפקד צוות, ולמפקד או מדריך של אותו אימון. הפונקציה `notify` אינה נגישה מהדפדפן — היא עוקפת את אותה בדיקה.
- **מגבלת קצב לכל קורא** (`bump_rate_limit`) על הכניסה, בחירת הקוד ובדיקת הפוש. הנעילה לפי חשבון מונעת ניחוש קוד; זו מונעת סריקת מספרים אישיים ממכשיר אחד.
- **מסך הכניסה אינו מחזיר שם או דרגה** לפני שהקוד אומת — אחרת הוא היה מדריך של היחידה, קריא לכל מי שיש לו הכתובת.
- **טופס ההצטרפות הפתוח מוגבל**: מספר אישי תקין בלבד, בקשה אחת למספר, תקרה של 100 ממתינות ו-10 בשעה. הודעת השגיאה זהה עבור ״כבר במערכת״ ו״כבר נשלחה בקשה״, כדי שלא יהיה אפשר לשאול דרכה מי נמצא ביחידה.
- **כותרות HTTP ומדיניות CSP** (`src/middleware.ts`): סקריפט רק מהמקור עצמו עם nonce לכל בקשה, `connect-src` מוגבל ל-Supabase של הפרויקט בלבד (כך שגם קוד שהוזרק אינו יכול לשלוח סשן החוצה), `frame-ancestors 'none'`, HSTS, ו-`Permissions-Policy` סגור. הדפים נטענים בכל בקשה כדי שה-nonce יגיע לסקריפטים.
- **ניתוק סשן פתוח** — `sessions_valid_from` על כל לוחם, ו-`me_row()` מקבל טוקן רק אם הוא הונפק אחריו והלוחם פעיל. איפוס קוד מנתק אוטומטית; יש גם ״ניתוק כל המכשירים״ בטופס הלוחם, ולוחם שמסומן מושבת מאבד גישה מיד. חל גם על ה-views המסכות, שרצות כבעליהן ולא רואות RLS.
- **תום סשן לאחר חצי שעה ללא פעילות** — באפליקציה שמותקנת על מסך הבית הלשונית לעולם אינה נסגרת, אז בלי זה הסשן היה חי עד שהמכשיר נכבה.
- **יומן פעולות** (`audit_log`) — מי הוסיף, מי שינה הרשאה, מי איפס קוד, מי יצר או מחק אימון. נכתב בטריגרים, נקרא בלבד, ואין לאיש הרשאת כתיבה או מחיקה עליו. נמצא ב**ניהול → יומן פעולות**.
- **קוד כניסה חלש נדחה** — הרשימה הנפוצה, ספרה חוזרת, רצף עולה או יורד, וזוג חוזר (1212).

```bash
npm run dev         # פיתוח
```

## 9א. תקופות, דו״חות וגיבוי

**ניהול → תקופות, דו״חות וגיבוי** (מנהל מערכת ומפקד חפ״ק):

- **סגירת תקופה** — התקופה שנסגרת נשמרת ב-`periods` עם שורה לכל לוחם: נוכחות מתוך האימונים ששובץ אליהם, דירוג המפקד, והסמכות שפקעו. מחושב פעם אחת ב-`close_period` ולא מחדש בכל צפייה, אחרת התשובה הייתה משתנה בכל פעם שמישהו מצטרף או עוזב.
- **פקודה לאימונים הבאים** — בוחרים מתוך האימונים שטרם בוצעו (כל מה שאינו ״הסתיים״ או ״בוטל״), ויוצא מסמך אחד: לו״ז כללי של כולם, ואחריו כל אימון במלואו — לו״ז יום, לוגיסטיקה, רכבים, תחמושת ומזון — עמוד לכל אימון. זהו בדיוק גוף הפקודה של אימון בודד (`orderHTML`), חוזר על עצמו, כדי ששני העותקים לא יוכלו לומר דברים שונים. גם לוואטסאפ.
- **דו״ח כשירות** — לתקופה הפעילה או לכל תקופה שנסגרה, להדפסה.
- **גיבוי מלא (JSON)** — כל היחידה בקובץ אחד, להורדה ולשמירה מחוץ למערכת.
- **גיבוי אוטומטי** — `/api/cron` כותב עותק לדלי `backups` בימי ראשון ב-03:00, שומר את ארבעת האחרונים, וקריא למנהלים בלבד דרך קישור חתום. בסיס נתונים מתארח אינו גיבוי.

## 11. תקלות נפוצות

**״חסרה הגדרת Supabase״** — `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` חסרים. שים לב שה-URL הוא הבסיס בלבד, **בלי** `/rest/v1/`.

**המערכת מבקשת לבחור קוד בכל כניסה מחדש** — `pin_hash` לא נשמר. מסלולי הכניסה כותבים אותו עם מפתח השרת, שאין לו JWT של משתמש, והטריגר `guard_people_self_edit` דחה בדיוק את זה. מתוקן ב-`supabase/patch-01-admin-rank.sql`; בדיקה: `select name, pin_hash is not null as has_pin from people;`

**מבקשים ממני להתחבר ל-Vercel / ״Log in to Vercel״ במקום מסך הכניסה** — שני מקורות אפשריים:

1. **הקישור שחילקת אינו כתובת הייצור.** כל דיפלוימנט מקבל כתובת ייחודית משלו
   (`hapak300-<hash>-<user>.vercel.app`) והיא מוגנת תמיד. חלק רק את הכתובת
   הקבועה של הפרויקט — Vercel → Project → **Domains**, זו שאין בה hash.
2. **Deployment Protection דלוקה.** Vercel → Settings → **Deployment Protection**
   → **Vercel Authentication** → **Disabled** (לפחות ל-Production), ואז Redeploy.

**איך בודקים בלי לנחש:** פתח בטלפון, בחלון פרטי, את `<SITE>/api/health`. אם חוזר
JSON בעברית — האתר פתוח וכל לוחם יכול להיכנס. אם מופיע מסך של Vercel — אחת משתי
הסיבות למעלה.

**נכנסים ומיד חוזרים למסך הכניסה** — `PIN_PEPPER`, `AUTH_DERIVE_SECRET` או `SUPABASE_SERVICE_ROLE_KEY` חסרים בין משתני הסביבה. הוסף ב-Vercel והרץ Redeploy.

**״המספר האישי לא רשום״ למי שכן הוספת** — בדוק שהמספר הוא בדיוק 7 ספרות ושהלוחם בסטטוס ״פעיל״.

**שינוי במכשיר אחד לא מופיע באחר** — Realtime לא מופעל לטבלה. בדשבורד: **Database → Replication** ← ודא שהטבלאות מהמיגרציה `0001` נמצאות בפרסום `supabase_realtime`.

**התזכורות לא נשלחות** — `select * from cron.job;` (קיים ופעיל?), ואז
`select * from cron.job_run_details order by start_time desc limit 5;` לראות מה קרה בהרצה,
ו-`select * from reminders_sent order by sent_at desc limit 10;` לראות מה כבר נשלח.
`401` בתשובה = ה-`CRON_SECRET` בפקודת ה-cron לא זהה לזה שב-Vercel.
